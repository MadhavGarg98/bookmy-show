# Async Order Processing Queue

This document details the asynchronous payment and order confirmation pipeline. 

## Section 1: Why Async?
Synchronous payment processing is the most dangerous anti-pattern in a high-traffic ticketing system. Calling a payment gateway like Razorpay or PayU takes anywhere from 200ms to 2,000ms. 

If the API waits for the payment gateway to respond before completing the HTTP request, it holds onto the PostgreSQL database connection for that entire duration.

**The Math (DB Pool Collapse):**
Using the formula from the concurrency strategy: `Connections held = (% non-payment RPS × 0.02s) + (% payment RPS × payment_hold_time_s)`
- If payment calls are synchronous, `payment_hold_time_s` = `2.0` seconds.
- Assume `max_connections = 500`, and 20% of traffic is payments.
- `500 = RPS × (0.8 × 0.02) + RPS × (0.2 × 2.0)`
- `500 = RPS × 0.016 + RPS × 0.4`
- `500 = RPS × 0.416`
- **RPS Limit ≈ 1,200 RPS**

By making payments asynchronous, the DB connection is held for only ~10ms while the initial 'pending' booking is written. This allows the API to serve tens of thousands of requests per second with the same 500 connections.

## Section 2: The Queue Message Format

When a user initiates payment, the API creates a `pending` booking, holds the seats, and publishes this JSON message to an AWS SQS queue.

```json
{
  "bookingId": "a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d",
  "userId": "u9x8y7z6-v5w4-3u2t-1s0r-9q8p7o6n5m4l",
  "eventId": 105,
  "seatIds": [4589, 4590],
  "totalAmount": 4000.00,
  "paymentToken": "tok_1N3xyz2eZvKYlo2C",
  "idempotencyKey": "idem_req_987654321"
}
```

**Field Explanations:**
- `bookingId` & `userId`: Identifiers needed to update the database state and send user notifications.
- `eventId` & `seatIds`: Included to immediately update seat statuses without requiring an extra DB query to join the `booking_seats` table.
- `totalAmount`: Passed to verify the captured payment matches the expected total.
- `paymentToken`: The token generated by the client-side gateway SDK, used by the backend to actually capture the funds.
- `idempotencyKey`: Prevents double-charging if the worker crashes and the SQS message is retried.

## Section 3: The Worker Logic

A pool of ECS Fargate workers constantly polls SQS. When a message is received, the worker executes:

1. **Read Message:** Receive the payload from SQS. (Message becomes temporarily invisible to other workers).
2. **Call Payment Gateway:** Make the HTTP call to capture the funds using the `paymentToken`.
3. **Handle Gateway Response:**
   - **SUCCESS Path:**
     1. `UPDATE bookings SET status = 'confirmed' WHERE id = payload.bookingId`
     2. `UPDATE seats SET status = 'booked' WHERE id = ANY(payload.seatIds)`
     3. Trigger SMS/Email notification.
     4. `DELETE` message from SQS.
   - **FAILURE Path (Card declined, insufficient funds):**
     1. `UPDATE bookings SET status = 'failed' WHERE id = payload.bookingId`
     2. `UPDATE seats SET status = 'available', held_until = NULL, held_by = NULL WHERE id = ANY(payload.seatIds)` (Releases seats back to the pool).
     3. Trigger failure notification to user.
     4. `DELETE` message from SQS (The processing finished successfully, even though payment failed).

## Section 4: Edge Cases

### Edge Case 1: API Crashes After SQS Publish
**Scenario:** The API writes to the DB, publishes to SQS, but the node crashes before sending the HTTP 202 response to the user.
**Result:** The user sees a 502/Timeout in their browser and assumes it failed. However, the SQS message is successfully processed by the worker. The payment goes through, and the booking is confirmed.
**Resolution:** The user receives an SMS/Email confirming the booking. Their UI, upon refresh, will pull their confirmed booking from the API. The `idempotencyKey` ensures if they aggressively retry checking out, they aren't double-charged.

### Edge Case 2: Payment Gateway Timeout
**Scenario:** The worker calls the payment gateway, but the connection times out. It is unknown if the payment succeeded.
**Result:** The worker does *not* update the database and does *not* delete the SQS message. It deliberately crashes or throws an error.
**Resolution:** The SQS visibility timeout expires, and the message is picked up again. On the retry, the worker uses the `idempotencyKey` to ask the gateway: "Did this transaction succeed?" preventing a double-charge.

## Section 5: SQS Configuration

- **Visibility Timeout: `30 Seconds`**
  *Justification:* Payment gateways usually respond within 2 seconds, but timeouts can take up to 10 seconds. We set visibility to 30s to guarantee the worker has completely died/timed out before letting another worker attempt the same message. This prevents two active workers from processing the same payment simultaneously.
- **Max Receive Count: `3` (before DLQ)**
  *Justification:* If a message fails 3 times, it implies a systematic error (e.g., a malformed payload or the payment gateway is hard-down), not a transient network glitch. After 3 attempts, SQS moves it to a Dead Letter Queue (DLQ). An engineer is alerted via CloudWatch, and the `pending` booking remains held until human intervention resolves it.
